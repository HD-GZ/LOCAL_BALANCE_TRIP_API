# 여행자 프로필 32유형 재설계 (MBTI 방식)

## 배경과 목표

현재 `travel_profiles` 테이블은 취향 5축 + 가치소비 5축을 각각 LOW/NEUTRAL/HIGH 3버킷으로 나눈 조합(약 5만 행)을 저장하고, NEUTRAL 축을 이름에서 생략하는 방식으로 39개의 가변 조합형 `type`을 만든다. 이로 인해:

- type 경우의 수가 많아 유형별 캐릭터 이미지를 제작할 수 없다.
- 같은 type이라도 description이 가치소비 조합마다 달라(5만 개 전부 유니크) "같은 유형 = 같은 정체성"이라는 공유 경험이 없다.

MBTI(4축 × 2극 = 16유형)와 같은 구조로 **5축 × 2극 = 32유형**의 고정 프로필 체계로 재설계한다. 유형별로 고유 코드·별칭·고정 설명·캐릭터 이미지를 1:1로 갖는다.

## 확정된 결정 사항

| 항목 | 결정 |
|---|---|
| 유형 개수 | 32개 (취향 5축 × 2극, 동행유형 포함) |
| 중간값(3점) 처리 | 서버 경계 규칙: 점수 ≤3 → LOW극, ≥4 → HIGH극. 설문·프론트 변경 없음 |
| description | 유형당 고정 1개. 가치소비 문장 제거 |
| 가치소비 5축 | 유형 판정에서 완전 제외. 응답의 `valueConsumption` 원점수 반환은 유지 |
| 이름 체계 | 5글자 코드 + 고유 한글 별칭 |
| 저장 방식 | `travel_profiles` 테이블 재설계(32행), Flyway 시드 |
| API 응답 | `propensityResult` 구조 유지. `type`에 "별칭 (코드)" 결합 문자열, `imageUrl` 필드 추가 |

## 축·코드 체계

코드 자릿수 순서는 여행지 → 소비기준 → 활동방식 → 여행스타일 → 동행유형. 열 글자가 모두 달라 코드만으로 축 구분이 가능하다.

| 자리 | 축 (필드) | LOW극 (≤3) | HIGH극 (≥4) |
|---|---|---|---|
| 1 | 여행지 (locality) | **H** 핫플 | **L** 로컬 |
| 2 | 소비기준 (frugality) | **P** 프리미엄 | **V** 가성비 |
| 3 | 활동방식 (experientiality) | **S** 감상 | **E** 체험 |
| 4 | 여행스타일 (vitality) | **R** 여유 | **A** 액티브 |
| 5 | 동행유형 (sociality) | **I** 혼행 | **G** 동행 |

예: `HPSRI` = 핫플·프리미엄·감상·여유·혼행.

## 도메인 로직

- `TravelProfileCode`를 `domain/propensity/model`에 추가한다. `Preference`의 5개 점수만으로 5글자 코드를 계산한다. 가치소비는 유형 판정에 쓰이지 않는다.
- 경계 규칙(≤3/≥4)은 이 클래스 한 곳에만 존재한다.
- 기존 `PropensityBucket`은 프로필 조회 용도로만 쓰였으므로 삭제한다.

## 테이블·엔티티

`V19__recreate_travel_profiles_for_32_types.sql`:

```sql
DROP TABLE travel_profiles;

CREATE TABLE travel_profiles (
    id BIGINT NOT NULL AUTO_INCREMENT,
    code CHAR(5) NOT NULL,
    nickname VARCHAR(100) NOT NULL,
    description VARCHAR(1000) NOT NULL,
    image_key VARCHAR(255) NULL,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uk_travel_profiles_code UNIQUE (code)
);

-- 이어서 32행 INSERT 시드
```

- `image_key`는 캐릭터 이미지의 S3 객체 키. 이미지 제작 전까지 NULL이며, 준비되면 배포 없이 DB UPDATE로 연결한다.
- `TravelProfile` 엔티티를 새 스키마로 재작성한다(`@Getter`, `create(...)` 정적 팩토리, `BaseEntity` 상속 유지).
- `TravelProfileRepository`는 `findByCode(String code)` 단건 조회로 단순화한다.

## 서비스·API 응답

- `PropensityService.findTravelProfile`은 `Preference` → 코드 계산 → `findByCode` 조회로 변경한다. 미존재 시 기존 `TRAVEL_PROFILE_NOT_FOUND` 흐름 유지.
- `PropensityResponse.InnerPropensityResultResponse`:

```json
{
  "propensityResult": {
    "type": "프라이빗 무드 컬렉터 (HPSRI)",
    "description": "…고정 설명…",
    "imageUrl": "https://stage.images.lb-trip.live/{image_key}"
  }
}
```

- `type`은 `"{nickname} ({code})"` 형식으로 DTO에서 조립한다. DB에는 code와 nickname을 분리 저장하므로 표기 형식 변경 시 데이터 수정이 불필요하다.
- `imageUrl`은 `image_key`가 있으면 CloudFront 베이스 URL과 조합해 반환하고, NULL이면 `null`을 반환한다. 베이스 URL은 `application.yml` 환경 변수로 관리한다.
- 기존 응답 필드(`preference`, `valueConsumption` 원점수)는 변경 없음.

## 사용자 데이터 영향

사용자별로는 원점수만 `propensities`에 저장되고 프로필은 조회 시마다 재계산되므로, **사용자 데이터 마이그레이션은 불필요**하다. 참조 테이블 교체와 분류 로직 변경만으로 기존 사용자 전원이 다음 조회부터 32유형으로 전환된다.

| LVEAG | 로컬 탐험 원정대장 | 일행을 이끌고 로컬의 체험거리를 알뜰하게 정복하는 여행자예요. 가성비 좋은 이색 체험을 찾아내는 데 능하고, 부지런한 일정으로 모두와 동네의 매력을 나눠요. |
